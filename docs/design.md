# ゲーム設計ドキュメント

Discord 連携型 FX トレーディングゲームの設計詳細。
規約・スタック・ディレクトリ構成は `../CLAUDE.md` を参照。

このドキュメントには**却下した案とその理由**も記載している。
同じ議論を蒸し返さないため、提案前に必ず確認すること。

---

## 1. コンセプト

### 核となる面白さ

> **プレイヤーの売買が実際に価格を動かす。**

単なる相場予想ゲームではなく、参加者自身が需給を作る。
20 人という小規模だからこそ、1 人の大口取引が可視的に相場を歪める。
この体験を最優先で守る。

### 1 日 1 時間という制約

取引可能時間は 1 日 1 時間のみ（具体的な時刻は未確定）。

これは制約ではなく**設計上の武器**。

- 全員が同時にログインするため、20 人でも「市場に人がいる」状態が作れる
- バラバラの時間に取引されると需給が噛み合わず過疎マーケットになる
- 毎日決まった時間に集まる習慣ができる

ただしこの制約は他の要素に波及する（減衰速度・claim のタイミング・
ポジション持ち越し・指値の約定タイミング）。以降で個別に扱う。

## 2. 価格モデル

### 2.1 基本式（2 層構造）

```
表示価格 = 基準価格(t) × (1 + 需給圧力 × exp(-λ × 経過時間))
           └─ 乱数由来の長期トレンド    └─ 取引による一時的な歪み
```

| 層 | 動く速さ | 役割 |
|---|---|---|
| 基準価格 | 日をまたぐ長期トレンド | 「この通貨は今上昇局面」という**相場観**を生む |
| 需給圧力 | 数分で減衰 | 取引の影響。**逆張りの旨味**を作る |

### 2.2 需給圧力の更新

```
買い注文時: 圧力 += k × (取引量 / 流動性深度)
売り注文時: 圧力 -= k × (取引量 / 流動性深度)
```

保持する状態は `基準価格` `需給圧力` `最終更新時刻` の 3 つのみ。

**逐次計算が可能:**

```
圧力(t₂) = 圧力(t₁) × exp(-λ(t₂ - t₁)) + Σ(t₁, t₂] の取引影響
```

### 2.3 なぜ平均回帰（減衰）が必須か

単純な「買うと上がる / 売ると下がる」だけを実装すると破綻する。

- 価格が上がりっぱなしで戻らない → **早く始めた人が永久に有利**、後発が勝てない
- 全員が「買い持ちして放置」が最適解になり、売る理由が消える
- 20 人規模では数人が結託すれば任意に価格を操作できる

減衰を入れることで:

- 大量購入で価格が跳ね、その後ゆっくり戻る → **高値掴みは損、暴騰時に売れば得**
- 価格の吊り上げは一時的にしかできず、結託の旨味が減る
- 「今この通貨は割高 / 割安」という判断軸が生まれる

### 2.4 λ（減衰速度）の設定

**半減期 3〜5 分**を目安とする。

1 時間セッションで数時間かけて戻る設定にすると、セッション中に一度も
回帰せず「買った者勝ち」に逆戻りするため。

### 2.5 基準価格の生成

**合成レート方式を採用**（実レート連動は却下 → §9.1）。

```
hash(通貨ID, floor(時刻 / 60秒)) → 疑似乱数 → 補間
```

各通貨に `drift`（トレンドの向き）と `volatility` を持たせ、
数日〜1 週間ごとにトレンドが反転するようにする。

これで「安定通貨だが儲からない」「暴れるがチャンスがある」という
キャラ付けができ、通貨を複数用意する意味が出る。

### 2.6 scale-to-zero との相性

**この式はバックグラウンドで価格を更新するプロセスを必要としない。**

読まれた瞬間に経過時間から計算するだけなので、インスタンスが落ちていても
次にアクセスされた時点で正しい価格が求まる。常時起動を避ける要件と噛み合う。

### 2.7 寄り付きギャップ

セッション外も基準価格は動き続ける（時刻の純関数なので自動的にそうなる）。

結果として翌日の開始時に価格が飛んでいる。

- ポジションを持ち越すか決める緊張感が生まれる
- 開始直後の数分が最もおいしい時間になり、**定刻ログインの動機**になる
- 実装コストはゼロ

「昨日の終値 → 今日の始値」のギャップを開始時に Bot が発表する。

### 2.8 パラメータは DB に持つ

`λ` `k` `流動性深度` `volatility` `drift` は `currencies` テーブルの列にする。

これがそのまま、将来の「ユーザーが通貨を作成して設定を変える」機能の実体になる。
コードに定数として埋め込まない。

## 3. データモデル

### 3.1 役割分担

| データ | 役割 |
|---|---|
| 乱数シード | **未来を生成する**（セッション中のリアルタイム価格算出） |
| `price_candles` | **過去を表示する**（確定した事実） |
| `trades` | 誰が何をしたか。約定価格も記録 |
| `events` | チャート上に「ここで暴落」と注釈を重ねる |

**シードは未来のため、キャンドルは過去のため。** 両方を再現に使わない（→ §9.2）。

### 3.2 毎分の tick でキャンドルを確定保存

```go
func (s *Service) Tick(ctx context.Context, now time.Time) error {
    minute := now.Truncate(time.Minute)

    currencies, err := s.db.ListCurrencies(ctx)
    if err != nil { return err }

    for _, c := range currencies {
        base := s.BasePrice(c, now)        // 乱数シード由来
        pressure := s.Pressure(c, now)     // 需給圧力（減衰込み）
        price := base.Mul(one.Add(pressure))

        agg, err := s.db.AggregateTrades(ctx, c.ID,
            minute.Add(-time.Minute), minute)
        if err != nil { return err }

        s.db.UpsertCandle(ctx, UpsertCandleParams{
            CurrencyID:    c.ID,
            MinuteAt:      minute,
            Open:          agg.FirstPrice.OrElse(price),
            High:          maxOf(agg.MaxPrice, price),
            Low:           minOf(agg.MinPrice, price),
            Close:         price,   // 取引ゼロでも価格は動くので必ず計算値
            Volume:        agg.TotalSize,
            BasePrice:     base,      // 人の影響を除いた価格
            PressureClose: pressure,
        })
    }
    return nil
}
```

**`Close` は必ず「その瞬間の計算価格」を入れる。**
取引ベースで OHLC を作ると、取引がない分に穴が空く。

### 3.3 データ量

1 日 60 分 × 通貨数。通貨 5 種なら **1 日 300 行**、1 年で約 11 万行。
無料枠にまったく影響しない。

24 時間市場ならこうはいかないが、1 日 1 時間なのでこの方式が成立する。

### 3.4 `base_price` / `pressure_close` 列の意味

チャート上に 2 本の線を描ける。

- 実際の価格（太線）
- **人がいなかった場合の価格**（薄い線 = `base_price`）

**乖離部分がそのまま「人間が動かした分」**として可視化される。
日次まとめで「本日 GBP は参加者によって本来より +8.2% 押し上げられました」
のような集計も SUM するだけで出せる。

### 3.5 High / Low の精度

毎分 1 回のサンプリングでは瞬間的なヒゲを捕捉できないが、

- 実際に**約定した価格**は `trades` に残るので取引範囲は正確
- 誰も取引していない瞬間の理論上のヒゲはゲーム的に意味がない

より滑らかにしたい場合、tick 内で 10 秒刻みに 6 点だけ基準価格を計算して
min/max を取る（基準価格は時刻の純関数なので過去の点も計算可能）。

### 3.6 tick の欠損

Cloud Scheduler の失敗やコールドスタートで tick が飛びうる。

**対応: 欠損は放置し、描画側で線形補間する。**
1 分の穴はチャート上ほぼ見えないため、複雑な穴埋めロジックを持つ価値はない。

## 4. 毎分 tick が担当する処理

Cloud Scheduler の cron を `* HH * * *`（取引時間の 1 時間だけ毎分）で設定。
1 日 60 回、無料枠 1 ジョブに収まる。

**時間駆動の処理をすべてここに集約する。**

```
tick(now):
  1. イベントの予兆投稿 / 発火判定
  2. 指値・逆指値の約定判定
  3. ロスカット判定
  4. キャンドル書き込み
  5. 市場ティッカーメッセージの編集（スパークライン更新）
```

**tick エンドポイントは必ず保護すること。**
OIDC トークン検証か共有シークレット。外部から叩かれるとイベントが暴発する。

## 5. イベントシステム

### 5.1 抽選と保存

セッション開始時に**その日のイベントを抽選して DB に書き込む**。
発火時刻を先に決めておき、tick が来た時に適用するだけにする。

1 日に 1〜2 回、相場が大きく動くイベントを発生させる。

```
events: id, session_id, currency_id, type, fire_at, magnitude, resolved
```

### 5.2 イベントの種類

効果が異なるものを混ぜる。

| 種類 | 効果 | 面白さ |
|---|---|---|
| 急騰 / 暴落 | 基準価格を一撃で ±5〜15% | 分かりやすい。ロスカット祭り |
| ボラ上昇 | `volatility` を数分間 3 倍に | じわじわ怖い |
| 流動性枯渇 | `liquidity` を下げる = 少額でも価格が大きく動く | 大口が暴れやすくなる |
| トレンド転換 | `drift` の符号を反転 | 持ち越し勢に効く |

### 5.3 予兆（重要）

発火の 30〜60 秒前に曖昧な予告を Discord に投げる。

```
📡 市場に何かの気配がします
   ……USD の様子がおかしい。何かは言いません。
```

**これによりイベントが「単なる運」から「乗るか降りるかの選択」に変わる。**

発表文はイベント種別ごとにテンプレを 5〜10 個持たせてランダム選択し、
飽きを防ぐ。トーンはユーモア寄り。

## 6. Discord 連携

### 6.1 認証

**Discord OAuth2 一本で完結させる。独自ログイン機構は作らない。**

```
Web:      「Discord でログイン」→ OAuth2 → Discord ユーザーID → セッション発行
Discord:  スラッシュコマンドのペイロードに Discord ユーザーID が最初から入る
```

**`users` テーブルの主キーを Discord ユーザーID にすれば、それだけで両者が繋がる。**
アカウント連携フロー・メール認証・パスワードリセットはすべて不要。

実装上の要点:

- scope は `identify` のみ。サーバー限定にするなら `guilds` を追加し、
  コールバック時に対象ギルド所属を確認
- Redirect URI に本番 URL とローカル（`http://localhost:8080/...`）の両方を登録
- 初回ログイン時に users 行を作成し初期資金を付与

将来的な拡張: `/login` コマンドでワンタイムトークン付き URL を ephemeral
（本人だけに見えるメッセージ）で返すと OAuth を踏まずにログインできる。MVP では不要。

### 6.2 Bot は HTTP Interactions 方式

| 方式 | 仕組み | 常時起動 |
|---|---|---|
| Gateway (WebSocket) | Bot が Discord に常時接続 | 必須 → **却下** |
| **HTTP Interactions** | Discord が こちらの URL に POST | **不要 → 採用** |

制約:

1. **3 秒以内に応答が必要。** Go バイナリ + Cloud Run ならコールドスタート
   数百 ms で余裕。Render 無料枠（スピンアップ約 1 分）は使用不可。
2. **Ed25519 署名検証が必須。** 標準 `crypto/ed25519` で 10 行程度。
   これがないと Discord への登録自体が通らない。

重い処理は deferred 応答（`type: 5`）で「考え中…」を 3 秒以内に返し、
後から PATCH で結果を送る。20 人規模の集計なら通常は直接返して問題ない。

### 6.3 Web と Discord の役割分担

```
Web      : チャート閲覧、新規注文、レバレッジ設定、詳細分析
Discord  : 残高確認、ランキング、既存ポジションの確認と決済、通知
```

Discord にもボタン・セレクトメニュー・モーダルがあるため、
以下は Discord 上で成立する。

- `/positions` → 保有一覧 + 各行に「決済」ボタン → 確認 → 決済完了
- `/price USD` → 現在価格 + 「買う」「売る」ボタン → 数量をモーダル入力

外出先で「今いくら？やばい、決済しとこう」ができる価値は大きい。
一方チャートを見ながらのレバレッジ調整は Web に誘導する。

### 6.4 市場ティッカー（Discord のチャート問題の解答）

**専用チャンネルに 1 つのメッセージを投稿し、毎分の tick でそれを編集し続ける。**

```
📊 マーケット  21:23 (残り37分)
━━━━━━━━━━━━━━━━━━
USD  152.44  ▲+1.2%  ▁▂▄▆█▇▅▄
EUR  164.10  ▼-0.8%  █▇▆▄▃▂▁▂
GBP  191.02  ▲+3.4%  ▁▁▂▃▅▇██  🔥
```

- **新規投稿ではなく編集なのでチャンネルが荒れない**
- スパークラインは `▁▂▃▄▅▆▇█` の Unicode 文字を並べるだけ。依存ゼロ・即描画
- 直近 8 本のキャンドル `close` を 8 段階に写像する
- 常にチャンネルを開いておけば「相場を眺めている」体験になり、
  Web を開かなくても状況が掴める

編集対象のメッセージ ID は DB に保存しておく。

### 6.5 チャートの補助手段

| 手段 | 内容 |
|---|---|
| ティッカー（上記） | **主軸。** 常時更新される概況 |
| 画像生成 | `/chart USD` で PNG を生成して添付（`go-chart` / `gg`）。ヘッドレスブラウザ不要、数十 ms |
| Embed の色 | `/positions` を含み益なら緑・含み損なら赤に。数字を読む前に状況が分かる |
| Web へのリンク | Embed に「詳細チャートを見る」ボタン。該当通貨ページへ直リンク |

### 6.6 スラッシュコマンド

**MVP**

- `/rank` 資金ランキング
- `/balance` 自分の資金
- `/claim` セッション開始時の資金取得（→ §7.2）
- `/today` 当日の増減ランキング
- `/positions` 保有ポジションと含み損益（決済ボタン付き）
- `/price <通貨>` 現在価格・変動率・スパークライン
- `/profile [@ユーザー]` 他人のプロフィール
  （20 人規模では他人の戦績が見えることが最大の燃料になる）

**MVP 後**

- `/history` 直近の取引履歴
- ランキングの軸切り替え（引数で: 総資産 / 当日 / 週間 / 勝率 / 単発最大利益 / 最大ドローダウン）

### 6.7 自動通知

- **大口取引の通知** — 「〇〇が USD を大量購入。価格が +3.2% 変動」
  価格影響がある設計なので、**これが他プレイヤーの行動トリガーになり市場が動き出す。**
  この機能の有無で体験が根本的に変わる。**MVP に含める。**
- **強制ロスカット通知**（→ §6.8）
- **イベント予兆・発生通知**
- **セッション開始 5 分前の予告 / 終了 5 分前の警告**
- **日次まとめ**（→ §6.9）

**毎日の定例ランキング投稿は行わない**（くどくなるため）。
日次まとめに統合する。

### 6.8 ロスカットの演出

ロスカットを「痛い」から「ネタ」に変える。

**称号ロールは翌セッション開始時に自動で剥がす。**
永続だと単なる晒し上げになるが、剥がれるなら「今日の称号」というネタになる。

ロール例: `退場者` `一敗地に塗れし者` `レバレッジの犠牲者` `本日の花火`

通知文もランダムテンプレ化する。

```
💥 〇〇 のポジションが消滅しました
   レバレッジ 25 倍。勇気ある判断でした。安らかに。
```

**いじりの強度は個別に切れるようにする。**
20 人の中に 1 人でも本気で嫌がる人がいると空気が悪くなる。
`users.roast_enabled` フラグを最初から用意する。

### 6.9 日次まとめ（セッション終了後）

```
🏁 本日の取引終了

🥇 〇〇      +142,300 (+38.2%)
🥈 △△       +88,100
🥉 □□       +51,900

💀 本日の被害者: ××（-92%）
📈 最大変動: GBP +14.3%（21:34 の暴落を的中させたのは 1 名のみ）
```

**勝者だけでなく「最大の負け」「最も無謀だったレバレッジ」「最速ロスカット」
などの賞を混ぜる。** 勝てなかった人にも見せ場を作る。20 人規模では特に重要。

### 6.10 ロール自動付与

定刻バッチで実行。

- 総資産帯による称号
- 上位 3 名の王冠ロール
- ロスカット者のネタロール（翌セッション開始時に剥がす）

**注意点:**

- Bot に `Manage Roles` 権限が必要
- **Bot 自身のロールを、付与対象の称号ロールより上位に配置する**
  （忘れると API が 403 を返す）
- Discord API のレート制限に注意。逐次処理 + リトライ、
  失敗しても次回で回復する**冪等な**作りにする

## 7. 経済設計

### 7.1 ポジションの持ち越し

**採用: B 案「持ち越し可、セッション外はロスカットしない」**

| 案 | 内容 | 評価 |
|---|---|---|
| A | 終了時に全ポジション強制決済 | 単純だが持ち越しの駆け引きが消える → 却下 |
| **B** | **持ち越し可。セッション外は判定せず、翌日開始時にまとめて判定** | **採用** |
| C | セッション外もロスカット判定 | 寝ている間に破産する。理不尽 → 却下 |

B により「寄り付きで一気に決着」という毎日のハイライトが生まれる。

### 7.2 資金配布（claim）

**セッション開始時に 1 回**。当初案の「12 時間おき」は取引時間とズレて
「取引できない時間に配布される」ことになるため変更した。

**資産下位バフを適用する:**

- 総資産が上位平均の一定割合を下回るプレイヤーは配布額が増える
- 例: 上位平均の 30% 未満なら 2 倍

これは救済であると同時に、インフレ対策（→ §7.4）と復帰動線（→ §7.5）を兼ねる。

### 7.3 手数料

インフレのシンクとして必須。回収分は消滅させる。

**片道 0.1〜0.3% から始めて調整する。**
1 時間しかないので高すぎると何もできなくなる。

**設定値は DB か環境変数に置き、デプロイなしで変更できるようにすること。**

### 7.4 インフレ対策

セッションごとに全員へ資金を配る以上、通貨供給量は増え続ける。
放置すると数ヶ月で数字がインフレし、初期からいる人との差が絶望的になる。

- 取引手数料をシンクにする
- claim を「総資産が少ない人ほど多い」ように傾ける
- ランキングを絶対額でなく**増加率**でも見せる

### 7.5 破産と復帰動線

レバレッジがある以上、必ず誰かが飛ぶ。
20 人規模で 1 人の離脱は痛いため、**復帰動線を最初から用意する。**

- 資産下位バフ（§7.2）
- `/reset` で初期資金に戻せる。ただし総資産ランキングから一時除外などの軽いペナルティ

**「破産してももう一回やれる」ことがゲームの寿命を伸ばす。**
むしろ破産を Bot がネタにすることで、失敗が楽しいイベントになる（§6.8）。

### 7.6 ランキングの軸を複数持つ

同じ人が総資産 1 位を独占しても、「今週の伸び率」なら新規参入者にも勝ち目がある。
**20 人規模では複数軸のランキングが特に重要。**

軸: 総資産 / 当日増減 / 週間増減 / 勝率 / 単発最大利益 / 最大ドローダウン

### 7.7 シーズン制

20 人・1 日 1 時間なら 1〜2 週間で上位が固定化する。

**2 週間〜1 ヶ月でリセットし、シーズン優勝者に永続ロールを与える。**
DB に `season_id` を最初から入れておけば後付けできる。

### 7.8 指値・逆指値の制約

常時起動しない構成では「価格が指値に達した瞬間」を監視できない。

**約定判定は「誰かが取引した時」と「毎分の tick」にまとめて行う。**
20 人規模なら遅延は気にならないはずだが、
**仕様として「約定は即時ではない」と明示する。**

強制ロスカットも同じ扱いになる。

### UPSERT（冪等性の確保）

```sql
-- name: UpsertCandle :exec
INSERT INTO price_candles (
    currency_id, minute_at, open, high, low, close,
    volume, base_price, pressure_close
) VALUES ($1,$2,$3,$4,$5,$6,$7,$8,$9)
ON CONFLICT (currency_id, minute_at) DO UPDATE SET
    high  = GREATEST(price_candles.high, EXCLUDED.high),
    low   = LEAST(price_candles.low, EXCLUDED.low),
    close = EXCLUDED.close,
    volume = EXCLUDED.volume,
    base_price = EXCLUDED.base_price,
    pressure_close = EXCLUDED.pressure_close;
```

tick が二重に走っても壊れず、high/low は正しく広がる方に更新される。


**再現ロジックは一切不要。** SELECT するだけ。

## 9. 却下した設計案（再提案しないこと）

### 9.1 実レート連動

外部 API から実際の為替を取得して基準価格にする案。

**却下理由:** 無料 API のレート制限が厳しく低頻度取得しかできない。
ゲームとしては合成レートのほうが変動幅を自由に調整でき、API 依存もゼロ。
（実レート連動そのものは将来の選択肢として残す）

### 9.2 過去チャートを取引履歴から毎回再計算する

シードと `trades` だけを保存し、需給圧力を畳み込みで再現する案。

計算量は問題ない（`圧力(t₂) = 圧力(t₁)×exp(-λΔt) + Σ影響` で逐次計算可能）。

**却下理由: 整合性が壊れやすく、「二重の真実」を生むため。**

ズレを生む要因:

- 丸め処理（float の演算順序、手数料の端数）
- ロスカットによる強制決済が圧力を持つか否か
- イベントによる `liquidity` 変動の正確な適用時刻
- 同一ミリ秒の取引順序
- トランザクションのリトライによる二重行

**1 つでもズレると「152.44 で約定したのにチャートは 152.41 を指す」状態になる。**
ユーザーは自分の約定価格を覚えているので必ず気づき、原因特定はほぼ不可能。

さらに深刻な問題として、価格ロジックが 2 箇所に存在することになる:

| | ロジック |
|---|---|
| セッション中 | 状態を保持して逐次更新 |
| 過去表示 | 履歴から再計算 |

**λ・手数料・イベント種別を調整するたびに過去のチャートが遡って変わる。**
パラメータ調整は頻繁に発生するため、実運用で必ず事故る。

**重要: キャンドル保存にしてもゲームの面白さは 1 ミリも減らない。**
セッション中の挙動は完全に同じ（誰かが買えば価格は上がる、ティッカーは動く、
大口通知は飛ぶ、逆張りの旨味もある）。キャンドルは結果を記録しているだけ。

さらに `base_price` 列により「人がいなかった場合の価格」との比較線という、
再現方式にはない見せ方が手に入る。

**もし将来どうしても再現方式を採るなら、以下が最低条件:**

1. 価格計算を単一の純粋関数に隔離し、セッション中もその関数を呼ぶ
2. float を一切使わない
3. `game_sessions` に当時の λ・手数料・k を保存し、再現時は当時の値を使う
4. 「セッション中の約定価格」と「再現値」の一致を毎日自動検証する

これらのコストとキャンドル 1 テーブルのコストを比べると、後者が圧倒的に安い。

### 9.3 Discord Gateway 方式の Bot

WebSocket 常時接続。**却下理由:** 常時起動が必須になり、無料枠構成が崩れる。

### 9.4 Render 無料枠

**却下理由:** スピンアップに約 1 分かかり、Discord の 3 秒応答制限を満たせない。

### 9.5 SQLite / ローカルファイル DB

**却下理由:** Cloud Run のファイルシステムは揮発する。単一バイナリでも DB は外部。

### 9.6 インメモリセッション

**却下理由:** インスタンスが常に落ちるため。DB に保持する。

### 9.7 毎日のランキング定例投稿

**却下理由:** くどい。日次まとめ（§6.9）に統合する。

### 9.8 GitHub Actions の cron による tick

**却下理由:** 最短 5 分間隔かつ遅延があるため毎分 tick に使えない。
tick は Cloud Scheduler、CI/デプロイは GitHub Actions という分担にする。

### 9.9 チュートリアルの MVP 実装

**MVP から除外**（必須ではないため）。

将来実装する際の方針: 画像スライド形式で十分。ただし説明順は
「用語 → 操作」ではなく **「1 回買って売る体験 → その意味の説明」** にする。
FX が分かりにくいのは概念のせいなので、先に触らせるのが最も効く。
初回ログイン時に少額の練習ポジションを自動で持たせるだけでも理解度が変わる。

## 11. 開発上の重要事項

### 11.1 Tick は時刻を引数で受ける

```go
func (s *Service) Tick(ctx context.Context, now time.Time) error
```

**テストで `Tick` を 1 分刻みに 60 回呼べば、1 日のセッションを数秒でシミュレートできる。**
バランス調整はこれで回す。

### 11.2 シードによるリプレイ

`game_sessions.seed` を保存しておくことで「あの日の相場をもう一度再生する」
検証モードが作れる。

「手数料を 0.3% にしていたらどうなったか」を実際の 1 日で試せるため、
パラメータ調整が非常に楽になる。

### 11.3 tick は通貨が増えても 1 回

全通貨をループして 1 トランザクションで書き込む。
通貨が 100 種になっても 1 分 1 回のまま維持できる設計にすること。
